## Hardware Acceleration: Tensor Cores, CUTLASS & Speculative Trees

### 1. Why LLM Decode is Memory-Bandwidth Bound (The Arithmetic Intensity Proof)
In autoregressive decode, the sequence generates one token per step ($M=1$). The GPU
must read all model weights (e.g. 14 GB for a 7B parameter bf16 model) from DRAM
to registers to perform a single GEMV operation:
$$\text{Arithmetic Intensity} = \frac{2 \times 7\times 10^9 \text{ FLOPs}}{14\times 10^9 \text{ Bytes}} = 1.0\text{ FLOP/byte}$$
On an H100 (3.35 TB/s HBM3 bandwidth, 2,000 TFLOP/s FP16 compute):
$$\text{Max Throughput} = 3.35\times 10^{12}\text{ B/s} \times 1.0\text{ FLOP/B} = 3.35\text{ TFLOP/s}$$
That is **less than 0.2% of the GPU's compute capability**. The compute units sit idle
waiting for memory. Batching requests reuses weights across $B$ tokens, raising arithmetic
intensity toward the roofline ridge point.

### 2. From CUDA Cores to Tensor Cores & CUTLASS
- **SIMT (CUDA Cores):** 1 instruction produces 1 scalar or vector operation per thread.
- **HMMA (Volta / Ampere Tensor Cores):** 1 warp (32 threads) executes a cooperative
  matrix multiply in a single instruction (`mma.sync.aligned.m16n8k16`).
- **WGMMA & TMA (Hopper / Blackwell):** 1 Warp Group (128 threads / 4 warps) executes
  asynchronous matrix multiplication (`wgmma.mma_async`), streaming data directly from
  shared memory into registers without ALU overhead, synchronized via `cuda::barrier`.
- **Why CUTLASS:** Modern engines use NVIDIA CUTLASS to decompose GEMMs into composable
  C++ templates that automate bank-conflict-free swizzled layouts and multi-stage software
  pipelining.

### 3. Tree-Attention Speculative Decoding (Stage 17)
Standard linear speculation proposes $K$ tokens in a single chain. The acceptance probability
decays exponentially ($a^K$).
- **Tree-Attention (Medusa / EAGLE):** Proposes a tree of multiple candidate branches.
- **Single Forward Pass Verification:** All candidate nodes are evaluated in a single
  forward pass of the target model.
- **Custom 2D Attention Mask:** Generated by `build_tree_mask`, ensuring candidate tokens
  only attend to their ancestors in the tree and the prompt history, isolating sibling
  branches.
- **Greedy Verification:** `verify_tree_greedy` traverses the tree, finds the longest valid
  path, and emits the accepted sequence plus an extra bonus token.
